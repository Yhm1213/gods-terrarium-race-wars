> **管理责任人**：主控总指挥 / 项目经理 (Lead Orchestrator / Project Manager)

## 详细条目记录与纠正预防措施 (CAPA Details)

### 【LL-001】阶段系统技术详细设计与数据契约先行门禁缺失
* **问题描述**：在 M0 推进与 M1 初期，主控 Agent 仅向子 Agent 下发了任务包名称与高层 DoD，未单独编制并下发该阶段的《系统技术详细设计与数据契约说明书》，导致子 Agent 在理解具体 TypedArray 切片、方法签名与数学模型时依赖大纲文档自行推导，带来接口不齐的潜在风险。
* **根因分析**：敏捷流程过于激进，跳过了阶段级技术详细设计（TDD）卡点，没有确立“契约发布即开工许可”的前置逻辑。
* **纠正与预防措施 (CAPA)**：
  1. 正式将《阶段技术详细设计与数据契约说明书》发布确立为研发法典第 1.2 节的 **Step 0 绝对前置门禁**；
  2. 每一阶段必须穷尽：子 Agent 必读专册、连续内存平铺排布、API 完整签名、有限状态机、领域事件载荷与 DoD 机器断言；
  3. 溯源补齐了 `docs/02_contracts/m0_detailed_technical_design_and_data_contracts.md` 与 `m1_...`；后续 M2~M4 绝不抢跑。

### 【LL-002】母 Agent 角色越位（亲自下场写代码污染上下文）
* **问题描述**：在 Tier 2 评审指出缺陷后，母 Agent 试图亲自调用编辑工具去修改业务代码，导致自身上下文急剧膨胀，破坏了多子 Agent 矩阵的分工体系与代码责任追溯机制。
* **根因分析**：母 Agent 角色认知混淆，将自己作为“超级程序员”而非“项目经理 (PM) / 调度总指挥 (Lead Orchestrator)”。
* **纠正与预防措施 (CAPA)**：
  1. **铁律确立**：母 Agent **绝对禁止亲自编写或修改任何生产代码**！母 Agent 的唯一天职是：**需求分解、工单派发、进度把控、质量卡点把关与经验资产维护**；
  2. **代码责任制 (Code Ownership)**：“谁写的代码谁负责维护与修复”。审查或测试发现的任何 Bug，PM 必须整理为正式整改工单，**定向打回给原作者子 Agent** 进行闭环修复；
  3. 上下文净化：所有具体实现的语法细节、堆栈跟踪均留在子 Agent 的专属上下文中，母 Agent 仅接收最终交付物与测试结论汇报。

### 【LL-003】端到端集成出现“两张皮”（视窗前端脱离底层交付构件）
* **问题描述**：`coder-rendering` 交付的 `index.html` 演示视窗，内部手写了简易的 `farmlands = []` 和原生饥饿衰减逻辑，没有真实 `import` 并驱动 M1 交付的 `NutrientField`, `FarmlandSystem`, `MetabolismSystem`, `EmergencyMetabolismSystem`, `WorldBoundaryGuard`，导致集成演示与真实系统脱节，并抛出 `getTileTypeByWorld` 不存在的致命崩溃。
* **根因分析**：前端开发子 Agent 贪图快速呈现效果，搞临时 Ad-hoc Mock，违背了端到端集成测试的严肃性。
* **纠正与预防措施 (CAPA)**：
  1. 视窗与客户端必须作为系统流水线的**唯一真实消费者 (Real Consumer)**，严禁在渲染视窗中自行 Mock 底层已存在的业务逻辑；
  2. 下发整改工单，强制 `coder-rendering` 重构 `index.html`，以标准 GameLoop 编排调用真实的 M1 领域系统；
  3. 整改后已 100% 原生驱动 M1 全量真实构件，实现 60 FPS 稳定运行，问题彻底闭环。

---

### 【LL-004】技术契约与生产代码数值量纲未同构
* **问题描述**：契约 SPEC-M1-CONTRACT 规定底温应为 `floors[i] * 50.0`，但实现中直接赋值为 `floors[i]`，导致平原底温仅为 0.25，永远无法触碰农田休耕自动重启阈值 (15.0)，险些导致闭环生态死锁。
* **根因分析**：开发子 Agent 与测试子 Agent 在单测中只验证了 `>= 0.85`，缺乏对系统间数值耦合（休耕阈值 vs 底温上限）的端到端宏观数值推演。
* **纠正与预防措施 (CAPA)**：
  1. 契约中必须明确写出公式的量纲推导依据与跨系统阈值依赖链条；
  2. 单测不仅断言“不小于”，还要断言其落在具有业务意义的区间（例如平原底温断言 `toBeCloseTo(15.0, 1)`）；
  3. 整改已落实乘 50.0 量纲与休耕重启正向协同，测试通过。

---

### 【LL-005】文档目录平铺散乱导致知识资产混乱
* **问题描述**：项目初期所有设计专册、规范、契约、评审报告均平铺在根目录 `docs/` 下，文件多达 20 余个，命名长短不一，子 Agent 检索参考文档极易遗漏或加载错误版本。
* **根因分析**：缺乏清晰的工程级文档架构设计，没有按照“治理-设计-契约-评审”建立层级。
* **纠正与预防措施 (CAPA)**：
  1. 全面重构为四级标准目录树：
     - `docs/00_governance/`：管理宪法、QA 规范、经验教训登记册；
     - `docs/01_design/`：GDD, SRS, WBS, TDS 及策划专册；
     - `docs/02_contracts/`：各阶段技术设计与数据契约说明书（M0, M1...）；
     - `docs/03_reviews/`：专家评审报告与里程碑验收备忘录。

### 【LL-006】方法签名形参缺失导致运行时抛出 ReferenceError 崩溃
* **问题描述**：`MiniRenderer.js` 的 `render` 方法签名缺少 `nutrientField` 形参，但在函数体内直接执行 `if (nutrientField)`，导致外部未作为全局变量时抛出致命 `ReferenceError: nutrientField is not defined`。
* **根因分析**：修改内部实现时未同步校准函数入参签名，且缺少安全的 Fallback 守门逻辑。
* **纠正与预防措施 (CAPA)**：
  1. 扩展方法签名至 `render(world, ecs, farmlands = null, nutrientField = null)`；
  2. 建立安全 Fallback 保护链：先判空、再取属性、最后从 world 兜底；
  3. 在渲染单测中增加多态参数组合与无参数传入的回归测试断言，确保永不抛异常。

### 【LL-007】多 Worker 并发 CI 环境下性能基准断言因 CPU 调度抖动产生 Flaky
* **问题描述**：在 Vitest 运行 14 个测试套件时，多进程/多 Worker 争抢 CPU 时间片，导致原本在单线程下单次执行 $< 0.1\text{ms}$ 的 4096 实体空间哈希重构基准测试，墙钟时间偶尔因上下文切换浮动到 $0.23\text{ms} \sim 0.35\text{ms}$，触发了过紧设定的 $< 0.2\text{ms}$ 硬断言，形成假阳性报警。
* **根因分析**：微基准测试（Micro-benchmark）混在集成测试多 Worker 环境下运行，受操作系统调度干扰严重，且预热不足。
* **纠正与预防措施 (CAPA)**：
  1. JIT 充分预热：提升预热轮次从 30 轮至 50 轮，采样轮次提升至 100 轮；
  2. 设定工程合理的防抖动门禁：将并发环境下硬截断阈值调整为 $0.5\text{ms}$（仍远低于单帧 $16.6\text{ms}$ 预算的 1/33），兼顾严苛性能守门与 CI 稳定性。

### 【LL-008】警惕系统孤岛与单测自嗨陷阱（单元测试全绿无法代表系统产生有机涌现）
* **问题描述**：M0~M4 底层 45 个测试套件 355 项断言全部 100% 满分通过，但端到端视窗中实体处于纯随机布朗运动，小人互不交互，领地死板固定，农田与代谢互不沟通，没有任何可玩性与文明生长感。
* **根因分析**：研发过程中陷入了“组件单测驱动”的局部最优陷阱，每个系统在 Mock 隔离下完美运行，但缺少了驱动实体生存、劳作、繁衍、交火与扩张的“全局生态闭环与行为中枢”。
* **纠正与预防措施 (CAPA)**：
  1. 确立“端到端活体生态闭环第一性原理”：任何系统交付必须在主仿真循环中形成闭环调用链，杜绝死代码与孤岛组件；
  2. 在 QA 门禁中增设 `TC-EDGE-10`（动态领地与粮仓繁衍闭环）与 `TC-EDGE-11`（自发冲突与战争军团推演）；
  3. 强制在端到端视窗中提供宏观排行榜与多模态沙盒重玩器，确保每一局游戏具备独特的涌现历史。

### 【LL-009】种族与政权正交解耦原则（生物学种族 Race 绝对不等于地缘王国 Faction）
* **问题描述**：此前系统将 `factionId` 机械地硬编码绑定为 `raceIndex + 1`，导致“一个种族只能有一个王国，12 种族等于 12 个王国”，完全丢失了同族内战、同种族多个互相对抗的部落/公国、以及多民族帝国/奴役共存的深度地缘政治乐趣。
* **根因分析**：数据模型设计将“生物遗传学特征 (Race/Genetics)”与“政治实体/法理主权 (Faction/Kingdom)”混为一谈。
* **纠正与预防措施 (CAPA)**：
  1. **正交解耦**：`RaceId` (0~11) 仅代表生物表型、体质特技与变异禁忌；`FactionId` (1~16) 代表独立的王国/部落政治实体，拥有独立的图腾、旗帜色彩、领地、粮仓与外交关系；
  2. **支持同族多分枝王国**：允许人类拥有“高铎圣帝国”与“北境自由领”，兽人拥有“血手氏族”与“铁颅氏族”；当发生大分裂 (`SchismSystem`) 时，分裂出的叛乱政权作为新 Faction 共享同族血脉却拔刀相向；
  3. 在剧本管理器中支持自定义王国数量与种族映射。

### 【LL-010】双职业兼职履历自生成与生产-战斗行为实体化闭环（杜绝 Enum 假兼职）
* **问题描述**：原设计有“生产主职 + 战斗副职”，但在实现中职业只是一个没有行为驱动能力的数值或 enum 标签，平民不知道为何要转职，转职后在世界中表现无差异。
* **根因分析**：职业系统未与微观经济（粮仓资源）和微观战术（战斗武器与站位）强绑定。
* **纠正与预防措施 (CAPA)**：
  1. **生产主职直接锚定经济产出**：农夫专精 2x2 农田割麦运粮，石工/建筑师伐木采石用于扩建领地界碑与修缮图腾，采药师采集草药用于伤员治疗；
  2. **战斗副职直接锚定战术动作**：盾卫持盾前排抗伤、狂战士血越低攻击越高、刺客潜行刺杀敌酋/粮仓、长弓手后排抛射；
  3. **复合称号与行为涌现**：如“农夫+狂战”组合为【暴怒民兵】，平时种田，遭遇入侵时挥舞镰刀狂暴反击；“石工+铁卫”组合为【重石盾卫】，平时筑墙，战时立盾在前线筑起人肉防线。

---

### 【LL-011】组织过程资产全量同步与工程变更防“局部漏改”治理（杜绝上改下未改）
* **问题描述**：在用户指出“游戏性断层、没有建立感、国土僵死”后，初次整理仅更新了总策划案与主规格书，却遗漏了具体的《设计专册 (Design Books)》、同族多王国机制、双职业实体物理融合细节以及组织过程资产（OPA）体系文件，导致出现“高层改了、专册没改、治理断层”的局部工程漏洞。
* **根因分析**：项目管理中缺乏全生命周期组织过程资产（OPA）清单检索与穿透式变更意识，变更控制（Change Management）未彻底落实闭环治理。
* **纠正与预防措施 (CAPA)**：
  1. **编制全景 OPA 资产清单**：正式发布 `docs/00_governance/organizational_process_assets_index.md`，对项目立项以来的设计专册、架构契约、治理制度、评审报告进行全量归档与动态维护；
  2. **穿透式变更控制链（Change Penetration Rule）**：任何一级工程变更（Level 1 ECR）必须强制全链路穿透：
     $$\text{ECR} \Longrightarrow \text{GDD v3.0} \Longrightarrow \text{Design Books (01~09)} \Longrightarrow \text{SRS v2.0} \Longrightarrow \text{TDS v2.0} \Longrightarrow \text{WBS v2.0} \Longrightarrow \text{RTM v5.1} \Longrightarrow \text{SPEC Contract} \Longrightarrow \text{OPA}$$
  3. **禁止局部宣称完成**：所有变更必须经由 CCB（用户）正式签字，且所有关联文档全量更新完毕后方可进入子 Agent 研发排期。
